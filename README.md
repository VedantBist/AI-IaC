# Infrastructure as Code for an AI-Based Prediction System

A local college project showing how Terraform can provision a Dockerized, multi-model AI prediction service. The browser dashboard calls a FastAPI controller; the controller manages Terraform operations; Terraform builds and runs the FastAPI model service.

```text
Frontend dashboard
        |
        v
FastAPI controller :9000
        |
        v
Terraform operation manager
        |
        v
Docker image / container :8001 -> :8000
        |
        v
FastAPI multi-model prediction service
        |
        v
scikit-learn model artifacts
```

## Technology stack

- Python, FastAPI, Uvicorn, joblib, NumPy
- scikit-learn datasets and estimators
- Docker and Terraform Docker provider
- Plain HTML, CSS, and JavaScript
- Local browser, Docker Desktop, and Terraform only

No cloud infrastructure, database, authentication system, Kubernetes, or message queue is required.

## Supported models

The registry in `ml/model_registry.py` is the single source of model metadata, input sizes, sample vectors, labels, and artifact paths.

| ID | Dataset | Algorithm | Task | Features |
| --- | --- | --- | --- | --- |
| `breast_cancer` | Breast Cancer | Logistic Regression | Binary classification | 30 |
| `iris` | Iris | Random Forest | Multiclass classification | 4 |
| `wine` | Wine | Decision Tree | Multiclass classification | 13 |
| `diabetes` | Diabetes | Linear Regression | Regression | 10 |
| `digits` | Digits | Logistic Regression | Multiclass classification | 64 |

Artifacts are stored in `ml/models/`. They are generated by `ml/train_all_models.py` and loaded when the AI service starts. Training does not run during API startup.

## Model and prediction flow

The frontend loads model metadata from `GET http://127.0.0.1:8001/models`, renders the selected model's input contract, and sends:

```json
{
  "model": "iris",
  "features": [5.1, 3.5, 1.4, 0.2]
}
```

The backend validates the model ID and exact feature count before selecting the artifact and predicting. Classification responses include a label and class. Regression responses include a numeric prediction:

```json
{"model":"iris","prediction":"Setosa","class":0}
```

```json
{"model":"diabetes","prediction":209.7564,"class":null}
```

The sample inputs are for demonstration only. The breast-cancer result is not a medical diagnosis.

## Docker and Terraform

The Dockerfile packages the backend, registry, and five artifacts. It starts Uvicorn on `0.0.0.0:8000`. Terraform builds `ai-iac-service:latest` from the repository root with the local Docker Buildx builder and manages `ai-iac-terraform` with host mapping `8001:8000`.

Terraform configuration is intentionally small and readable for a viva. The controller runs all commands with `cwd=terraform/` and only exposes predefined plan, apply, and destroy actions.

## Controller endpoints

- `GET /` - controller health
- `GET /status` - reconciled Terraform, Docker, container, and AI health state
- `GET /diagnostics` - controller, Terraform, Docker, model, operation, and AI diagnostics
- `GET /models` - registry metadata fallback when the AI container is offline
- `GET /operations/active` - active operation, if any
- `GET /operations/{operation_id}` - operation status and stored output
- `POST /plan` - asynchronous Terraform plan
- `POST /deploy` - asynchronous Terraform apply
- `POST /destroy` - asynchronous Terraform destroy

The AI service exposes:

- `GET /` - service health
- `GET /models` - public model registry metadata
- `POST /predict` - model-aware prediction

## Reliability and recovery design

Terraform mutations run through a single in-process operation manager. Every plan, deploy, or destroy receives an operation ID and runs in a controlled background thread with a five-minute process limit. The subprocess uses a fixed working directory, a predefined argument list, captured output, and a process group for timeout cleanup.

The controller writes the latest operation record to the system temporary directory as `ai-iac-project-operation.json`. It is not a database and is outside the Uvicorn reload watch path. It lets a restarted controller inspect the last operation, while actual truth still comes from Terraform state, Docker inspection, and the AI health endpoint.

`GET /status` does not trust a Python `is_deployed` flag. It reports `BUSY` when Terraform is actually running, checks Docker with `docker inspect`, and checks the AI service with `GET http://127.0.0.1:8001/`. If a persisted operation says `RUNNING` but no Terraform process exists after restart, it is marked `RECONCILED` and infrastructure is inspected normally rather than remaining stuck forever.

The frontend starts in `UNKNOWN`, recovers any active operation on page load, polls every 1.5 seconds, stops on a terminal operation state, and performs final reconciliation after its five-minute polling limit. Duplicate mutations receive the current operation conflict instead of starting a second Terraform process.

## Prerequisites

- Python 3.10 or newer
- Docker Desktop with the Docker engine running
- Terraform 1.x on `PATH`

## Installation

From the project root:

```bash
python -m venv venv
source venv/bin/activate
pip install fastapi uvicorn joblib numpy scikit-learn
python ml/train_all_models.py
terraform -chdir=terraform init
terraform -chdir=terraform validate
```

## Running locally

Terminal 1:

```bash
uvicorn controller.main:app --port 9000 --reload
```

Then open `frontend/index.html` in a browser. The dashboard will load the model registry and reconcile infrastructure automatically.

### Plan

Click **Plan infrastructure**, or run:

```bash
curl -X POST http://127.0.0.1:9000/plan
```

Poll the returned operation ID:

```bash
curl http://127.0.0.1:9000/operations/<operation_id>
```

### Deploy

Click **Deploy infrastructure**, or use the controller. Do not run a second apply while an operation is `RUNNING`.

```bash
curl -X POST http://127.0.0.1:9000/deploy
```

Verify:

```bash
curl http://127.0.0.1:9000/status
curl http://127.0.0.1:8001/
docker ps
```

### Predict

Select any model in the dashboard and use its sample input. The frontend validates the feature count before sending the request. The API can also be called directly with the model-specific payload.

### Diagnostics

Click **System diagnostics** or call:

```bash
curl http://127.0.0.1:9000/diagnostics
```

The response distinguishes a running Docker container from an online AI service.

### Demo mode

The dashboard's deployment flow is deliberately explicit: inspect status, deploy if needed, wait for the operation ID to complete, then run a sample prediction. Infrastructure is not destroyed automatically. After the demonstration, click **Destroy infrastructure**.

### Destroy

Confirm the dashboard action, or call the controller directly:

```bash
curl -X POST http://127.0.0.1:9000/destroy
```

Poll until `COMPLETED`, then verify that Terraform is `READY` and Docker/AI are `OFFLINE`.

## History and UI state

Deployment and prediction history are kept in browser `localStorage`; no database is used. The dashboard has explicit `UNKNOWN`, `PLANNING`, `DEPLOYING`, `READY`, `DESTROYING`, `OFFLINE`, `BUSY`, `ERROR`, and `TIMEOUT` states. Refreshing the browser re-queries the controller instead of trusting stale page memory.

## Troubleshooting

- **Controller unavailable:** start `uvicorn controller.main:app --port 9000 --reload` from the project root.
- **Terraform unavailable:** verify `terraform version`, then run `terraform -chdir=terraform init`.
- **Docker unavailable:** start Docker Desktop and check `docker ps`.
- **AI service offline:** inspect `/status`, then inspect the operation record and `docker logs ai-iac-terraform`.
- **Operation busy:** poll `/operations/active`; do not start another plan, apply, or destroy.
- **Model artifact missing:** run `python ml/train_all_models.py`, then rebuild or redeploy the image.
- **Port conflict:** keep Terraform's `8001:8000` mapping and update the frontend URL only if the mapping is intentionally changed.

## Limitations and future scope

This is a local educational demonstration. It has no authentication, production monitoring, cloud deployment, model registry server, medical validation, or durable multi-user job queue. Future work could add automated tests, versioned model artifacts, richer metrics, and a cloud target without changing the educational core.
